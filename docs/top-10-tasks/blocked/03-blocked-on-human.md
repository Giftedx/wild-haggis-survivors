## 2. Approve auth provider

**Recommendation:** Magic-link (email-only, one-time tokens, 15-min expiry,
HttpOnly cookie session). Implemented in ~50 lines of Worker code.
**Email provider:** Resend (free tier covers 3k/month; first $0).
**No password auth.** No OAuth at v1 (charter §Risk descope lever).
**See:** `docs/P3_BACKEND_DECISION_MATRIX.md §4` ("Auth provider sub-decision").

**Why this is a human call:** privacy-sensitive; the auth provider is the
only third party (besides Cloudflare) that touches user PII (email).

- [ ] **Approve magic-link via Resend**, OR
- [ ] Pick alternative email provider (Postmark, SES, Mailgun): ____
- [ ] Add OAuth (Google / Apple) at v1? Default no — defer to v2 if
  magic-link friction surfaces.

## 3. Approve privacy policy + GDPR controller details

The charter requires `/privacy.html` linked from Settings. This needs
real legal text the maintainer is comfortable signing as data controller.

**Required content (RGPD / UK GDPR Article 13):**
- Identity of data controller (real name + jurisdiction).
- What data is processed (email + opaque save blob).
- Why (functional: cross-device save sync).
- Lawful basis (consent — opt-in, withdrawable).
- Retention (until account deletion request, then ≤30 days).
- Right to access, rectify, delete, export, complain to ICO (UK) or
  appropriate supervisory authority (EU).
- Contact email for data-subject requests.

**Why this is a human call:** the data-controller statement is a legal
declaration the agent cannot make on the maintainer's behalf.

- [ ] Provide controller name + address.
- [ ] Provide data-subject-request email (default: same as
  `michael.mcmillan93@gmail.com` per project memory, but a separate
  inbox is recommended for hygiene).
- [ ] Approve plain-language draft once written. (Skeleton can be
  generated by the agent on demand; stakeholder owns the legal substance.)

## 4. Approve conflict-resolution UX

**Recommendation:** see spec doc `docs/specs/2026-04-26-cloud-save-conflict-ux.md`.
The implementation favours Last-Writer-Wins with a one-time prompt on
sign-in if the cloud has a newer save than the local. Charter §Phase 2.2
allows this.

**Why this is a human call:** the prompt copy lives in the Hearth voice
register and changes the player's first impression of the cloud feature.

- [ ] **Approve LWW + sign-in prompt** as designed, OR
- [ ] Request changes (e.g. always-newer wins, three-way merge). Note:
  three-way merge is multi-week additional work — Soul Charter says
  "kindness over correctness" anywhere this risks losing player work, so
  the spec biases toward "show timestamps, let the player choose".

## 5. Approve cost ceiling alarm

The charter §Risk says backend cost should track from day one. The
matrix doc projects $0/mo at 10k MAU but a runaway bug (e.g. infinite
sync loop on a borked client) could bill against Workers requests.

**Recommendation:** Cloudflare-native billing alert at $5/mo, escalating
email at $10/mo. Pause writes (toast: "Cloud sync paused — please update
the game") at $20/mo via Worker feature flag.

- [ ] **Approve alarm thresholds** ($5 / $10 / $20).
- [ ] Provide alert-email address.

---

## 6. Approve account-deletion latency

Charter says "within 30 days" (GDPR maximum). Real-time deletion is
trivial in the recommended stack — the question is whether to keep a
"recoverable for N days" grace window so a player who hits delete by
mistake isn't immediately wiped.

**Recommendation:** soft-delete with 7-day grace; hard-delete after.
Player gets one "undo" email link.

- [ ] **Approve 7-day soft-delete + 7-day undo email**, OR
- [ ] Pick alternative window: ____ days.

## What ships in this branch (without unblocking)

The following are landed and CI-green; they're the parts of P3 that do
not depend on backend selection:

1. **`CloudSaveEnvelope` type** + serialization round-trip tests
   (`src/cloud/cloudSaveEnvelope.ts`).
2. **`buildCloudSaveEnvelope` / `parseCloudSaveEnvelope` pure helpers**
   that wrap the existing `whs_save` payload without mutating its
   schema.
3. **`detectCloudSaveConflict`** — pure helper for LWW comparison given
   `(localEnvelope, remoteEnvelope)`. Returns one of `'local-newer' |
   'remote-newer' | 'in-sync' | 'conflict-ambiguous'`.
4. **`CloudSaveClient` interface** in `src/cloud/cloudSaveClient.ts` —
   the contract the eventual Worker connector implements. A
   `MemoryCloudSaveClient` test double ships for Vitest coverage.
5. **`cloudSaveOptIn` setting** added to `SettingsManager` (default
   `false`); UI placeholder lives behind a `?cloudSavePreview=1` URL
   flag and renders a "Coming soon" stub. No live network calls.
6. **Documentation:** matrix (`docs/P3_BACKEND_DECISION_MATRIX.md`),
   conflict-UX spec (`docs/specs/2026-04-26-cloud-save-conflict-ux.md`),
   ADR (`docs/adr/0006-cloud-save-backend.md`, accepted 2026-05-09), this
   blocked doc.
7. **No Phaser scene changes outside the gated preview flag.** The
   live Settings panel and MenuScene render unchanged when
   `cloudSavePreview` is absent.

When unblocked, the next session's wiring is:

1. Stand up Cloudflare Worker (sub-30 min once D1 is provisioned).
2. Implement `WorkerCloudSaveClient` against the `CloudSaveClient`
   interface — the existing tests cover the contract.
3. Promote the Settings UI placeholder to live by default (drop the
   URL gate).
4. Add the e2e Playwright spec the charter §Verification path
   requires.

The infrastructure shipped now intentionally minimises the surface that
needs review on unblock — the Worker is purely a CRUD endpoint over
the envelope; everything else (offline queueing, conflict detection,
toast wiring) is already tested in this branch.
